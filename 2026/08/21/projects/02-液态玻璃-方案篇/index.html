给博客做一套液态玻璃（二）：架构怎么搭

发表于2026-08-21|更新于2026-08-21|projects
|总字数:1.6k|阅读时长:5分钟|浏览量:

适用读者：上一篇讲了玻璃的光学原理，这一篇讲怎么把它变成一个能跑在真实博客上、不拖垮性能、不和主题打架的系统。

三条约束

动手之前，先把限制写下来。这三条决定了后面所有的设计选择：

  1. 不能 fork 主题。Butterfly 会更新，改了主题源码就等于放弃升级。
  2. 同屏 30 个玻璃面。文章页上卡片、侧栏、导航、代码块、表格、引用块全是玻璃。
  3. 不能降级成毛玻璃。性能不够的时候可以砍效果，但砍到最后必须还是玻璃——退回 blur() 等于承认失败。

分层

五个文件，每个只干一件事：

文件 职责
glass-sdf.js 距离场 → 位移贴图
glass-core.js 渲染引擎，选择渲染器、构建并缓存滤镜
glass-performance.js FPS 采样、分级降级、视口预算
glass-motion.js 滚动边缘、触摸按压、morph
glass-adapter.js 把 Butterfly 的选择器映射成玻璃权重

关键在于依赖方向是单向的：适配器知道 Butterfly，引擎不知道；引擎知道渲染器，材质系统不知道。换主题只需要重写适配器里的一张表。

一、材质系统：六档权重

最容易犯的错是「给卡片加个玻璃 class」。那样会变成「玻璃卡片 + 普通卡片」的割裂设计。

正确的做法是：页面上所有的面都是玻璃，只是权重不同。

六档权重，每档定义一组光学参数：

权重 折射 斜边宽 用在哪
soft 34 20 导航栏、标签、分页
medium 60 74 侧栏卡片、目录
strong 94 100 文章卡片、正文容器
dense 58 48 代码块、表格、引用
floating 84 88 搜索框、抽屉

参数全部是 CSS 自定义属性，不是 JS 常量：

这样做的好处在后面会不断兑现：主题切换、媒体查询、性能降级，全都能靠 CSS 自己完成，不需要 JS 往返。JS 只负责在需要生成贴图时把它们读出来。

为什么要延迟再跑一次？因为 Butterfly 在 DOMContentLoaded 之后才会改 DOM——它把宽表格包进 .table-wrap、动态构建目录。第一遍扫描时这些元素还不存在。

这里我踩过一个坑：适配器里写的是 .relatedPosts .relatedPosts-list > div，而这个版本的 Butterfly 实际生成的是 <a class="pagination-related">。选择器匹配了 0 个元素，导致文章底部是全站唯一没有玻璃的区域，而且不会报错——静默失效。

教训：靠选择器耦合外部主题时，一定要验证匹配数量，别假设它匹配上了。

小结

设计决策 原因
参数放 CSS 变量 主题/媒体查询/降级不需要 JS 往返
按几何缓存滤镜 30 个面 → 6 张贴图
尺寸量化到 8px 亚像素差异不再各生成一张
渲染器抽象 跨浏览器降级，将来能换 WebGL
降级留底线 砍到最低也还是玻璃
主题知识集中一处 换主题只改一张表
